Umsetzung — Schritt für Schritt

Sechs Schritte. Jeder lässt die App benutzbar, hat ein prüfbares Abnahmekriterium und ein Budget aus einer echten Messung. Wer diesen Plan liest, kann anfangen, ohne nachzufragen.

Die zwei letzten offenen Punkte — hiermit entschieden

Beide waren als Annahme markiert. Hier werden sie festgelegt, damit beim Bauen nichts geraten wird.

PunktFestlegungBegründung
Tab-Leiste im Einzelchat-Modus Verhält sich wie heute — sie zeigt die offenen Chats des Fensters. Der Rückweg in den Workspace läuft über die Seitenleiste (E2), die Leiste muss ihn also nicht liefern. Alles andere wäre eine zweite Bedienlogik ohne Gegenwert.
Workspace in einem zweiten Fenster öffnen Er wandert. Das erste Fenster fällt auf Einzelchat-Ansicht zurück und zeigt den zuletzt fokussierten Chat. Ablehnen wäre eine Fehlermeldung auf eine sinnvolle Handlung. Wandern entspricht dem, was Fenstersysteme sonst tun, und E9 verbietet nur die gleichzeitige Anzeige.
S1

Die Engine als pure Logik

größter Einzelschritt

Kein SwiftUI, kein AppKit, keine Abhängigkeit zum Store. Nur Daten hinein, Daten heraus — und damit vollständig unter Tests. Das ist die Voraussetzung dafür, dass der spätere Umbau der 75 Aufrufstellen mechanisch statt riskant wird.

Neue Dateien

DateiInhalt

Die Engine-Schnittstelle, vollständig

enum LayoutEngine {
    // ─ Mitgliedschaft ─────────────────────────────────────────

    /// Fügt einen Chat hinzu. Bei `automatic` ordnet die Engine ihn ein;
    /// bei `manual` kommt er in die zuletzt fokussierte Zelle als Stapel.
    static func add(_ session: UUID, to layout: WorkspaceLayout,
                    focused: UUID?) -> WorkspaceLayout

    /// Nimmt einen Chat heraus (× am Tab, E10). Wird die Zelle dadurch
    /// leer, verschwindet sie und die Fläche verdichtet sich (E4/F4).
    static func remove(_ session: UUID, from layout: WorkspaceLayout) -> WorkspaceLayout

    /// Ein beendeter Chat verschwindet aus JEDEM Layout — Invariante aus
    /// E8. Wird zentral beim Sessionende gerufen, nicht pro Ansicht.
    static func purge(_ session: UUID, from layouts: [WorkspaceLayout]) -> [WorkspaceLayout]

    // ─ Anordnen ───────────────────────────────────────────────

    /// Zwei Zellen tauschen ihre Plätze. Bei `automatic` heißt das:
    /// Reihenfolge in `cells` tauschen. Bei `manual`: Blätter tauschen.
    static func swap(_ a: UUID, _ b: UUID, in layout: WorkspaceLayout) -> WorkspaceLayout

    /// Chat auf eine Zelle ziehen: ersetzt deren Inhalt (äußerer Ring)
    /// oder legt ihn auf den Stapel (innerer Kern) — F2.
    static func drop(_ session: UUID, onto cell: UUID,
                     mode: DropMode, in layout: WorkspaceLayout) -> WorkspaceLayout

    /// Chat auf eine Trennlinie ziehen (E7): dort entsteht eine neue
    /// Fläche, und die Anordnung wird dadurch `manual`.
    static func insert(_ session: UUID, atEdge edge: Edge, of cell: UUID,
                       in layout: WorkspaceLayout) -> WorkspaceLayout

    /// Zurück zur automatischen Anordnung (F6). Der Baum wird verworfen,
    /// Zellen und Stapel bleiben.
    static func resetToAutomatic(_ layout: WorkspaceLayout) -> WorkspaceLayout

    // ─ Sichtbarkeit ───────────────────────────────────────────

    /// Welcher Chat einer Zelle sichtbar ist.
    static func activate(_ session: UUID, in layout: WorkspaceLayout) -> WorkspaceLayout
}

enum DropMode { case replace, stack }
enum Edge { case leading, trailing, top, bottom }

Die Geometrie

enum LayoutGeometry {
    /// Berechnet für jede Zelle ihr Rechteck. Bei `automatic` aus der
    /// Zellenzahl, bei `manual` aus dem Baum.
    ///
    /// `minimum` setzt die weiche Grenze aus F7 durch: Passt eine
    /// weitere Fläche nicht mehr in Mindestgröße, wird gestapelt statt
    /// geteilt. Vorgabe 80×24 Zeichen, umgerechnet über die Zellmaße.
    static func frames(for layout: WorkspaceLayout, in bounds: CGRect,
                       minimum: CGSize) -> [UUID: CGRect]

    /// Wie viele Spalten/Zeilen die automatische Anordnung bei n Zellen
    /// wählt. Ausgelagert, weil es die meistgetestete Einzelregel ist.
    static func automaticArrangement(cellCount: Int, aspect: CGFloat) -> (columns: Int, rows: Int)
}
Vorlage ist der HTML-Zwilling

Jede dieser Funktionen existiert dort als JavaScript und ist mit echter Maus erprobt: reflowAuto, buildAutoTree, framesOf, swapCells, replaceInCell, dropSession, throwIn. Die Übersetzung nach Swift ist Fleißarbeit mit bekanntem Ergebnis — nicht Entwurf.

Abnahme
  • Jede Invariante aus Paket 01 hat mindestens einen Test, der sie verletzt und prüft, dass der Normalisierer sie repariert
  • Jede Engine-Funktion hat einen Test für den Normalfall und einen für den Randfall (leeres Layout, letzte Zelle, unbekannte ID)
  • LayoutGeometry.frames gibt bei gleichen Eingaben immer dieselben Rechtecke — Rundung auf ganze Punkte, damit keine Fugen entstehen
  • Kein Import von SwiftUI oder AppKit in den vier neuen Dateien. Prüfbar per grep.
S2

Modell und Migration

klein, aber unumkehrbar

Erst wenn S1 steht. Die Migration wird gegen echte v4-Daten getestet, nicht gegen konstruierte.

Was passiert

SchrittDatei
AgentUIState.currentSchemaVersion auf 5Models/AgentUIState.swift:114
Migration v4 → v5 als pure FunktionModels/AgentUIState.swift:271ff (bestehender Pfad)
Rohsnapshot der v4-Datei vor der Umstellungneben agent-ui-state.json, Muster wie die Generationen-Backups
AgentGridWorkspace bleibt vorerst bestehenwird erst in S6 entfernt
Die Migration ist die einzige unumkehrbare Stelle

Deshalb: Rohsnapshot vor dem ersten Schreiben, und die Migration läuft genau einmal, erkennbar an der Schemaversion. Schlägt sie fehl, darf sie nicht bei jedem Start erneut denselben Schaden anrichten.

Bestand wird als manual übernommen (Paket 01): Die bestehende Anordnung bleibt exakt erhalten. Der Weg zur Automatik ist der sichtbare Schalter aus F6.

Abnahme
  • Migration mit einer echten agent-ui-state.json aus dem Feld getestet, nicht nur mit erzeugten Daten
  • Jedes v4-Layout ergibt ein v5-Layout mit denselben Chats an denselben Stellen — als Test, nicht als Sichtprüfung
  • Ein absichtlich kaputtes v4-Layout macht nicht die ganze Datei unlesbar
  • Zweiter Start migriert nicht erneut
S3

Anzeigen — ohne Interaktion

der Terminal-kritische Schritt

Das Layout wird gezeichnet, mehr nicht. Kein Ziehen, kein Zoom. Ziel ist ausschließlich: Terminals überleben jede Anordnungsänderung.

Was gebaut wird

DateiInhalt
Views/Workspace/WorkspaceLayoutView.swiftZeichnet die Rechtecke aus LayoutGeometry.frames
Views/Workspace/WorkspaceCellView.swiftEine Zelle: aktiver Chat plus Stapelleiste, wenn mehr als einer
Die eine Regel, an der dieser Schritt hängt

Ein Terminal darf beim Umsortieren niemals neu aufgebaut werden. Ein neuer PTY heißt: Scrollback weg, laufender Befehl weg. Das wäre schlimmer als jedes Layoutproblem.

Technisch: Die Identität einer Pane ist die Session-ID, nicht ihre Position. In SwiftUI heißt das .id(sessionID) auf der Terminal-Ansicht und keine Verschachtelung, die bei Umsortierung die Sicht-Identität ändert. Der Zähler pane.mounted deckt jeden Verstoß auf.

Abnahme
  • Der wichtigste Test: In ein Terminal tippen, Layout ändern, Text ist noch da — und pane.mounted ist nicht gestiegen
  • Chat schließen → Fläche verdichtet sich, übrige Terminals unberührt
  • sidebar.workspaceChangeFollowUp reißt sein 50-ms-Budget nicht
  • Neun Flächen mit Last: kein Eintrag von main_thread_freeze im Log
S4

Ziehen und Trenner

der riskanteste Schritt

Erst jetzt, auf gesichertem Fundament. Hier steckt der bekannte Präzedenzfall: Im Mai 2026 hat SwiftUIs Drag-API mit LazyVStack die App eingefroren (Fix 60ca683, Kommentar in AgentChatsSidebarViews.swift:199).

Vorgehen

TeilWie
Zeigegerät statt Drag-APIWie im Zwilling: Schwelle von 4 Punkten, dann Ziehen. Kein .draggable.
ZielbestimmungPure Funktion: Mausposition plus Rechtecke ⟶ Ziel (Zelle-ersetzen · Zelle-stapeln · Kante). Vollständig testbar ohne Maus.
VorschauPflicht, nicht Zierde: Ohne sichtbare Zone ist F2 ein Ratespiel.
Trenner ziehen: dehnen, nicht ändernSiehe Messung. Während des Ziehens nur die Darstellung strecken; die echte Größenänderung erst beim Loslassen.
Warum das Dehnen von Anfang an eingeplant sein muss

Gemessen: Neun Flächen kosten 11,24 ms allein auf der Terminal-Seite, plus etwa dieselbe Menge für die Neuzeichnung durch die laufenden Programme — rund 24 ms. Ein 60-Hz-Bild hat 16,7. Wer erst durchreicht und später dehnen will, muss die gesamte Geometrie-Kette umbauen, weil überall unterschieden werden muss, ob eine Größe vorläufig oder endgültig ist.

Abnahme
  • Zielbestimmung vollständig unter Tests — jede Zone, jede Kante, jeder Randfall
  • Trenner ziehen bei neun Flächen: grid.dividerTick unter 16 ms
  • Kein main_thread_freeze während einer Minute Dauerziehen
  • Ein Klick bleibt ein Klick — unter 4 Punkten Bewegung wird nichts gezogen
  • Terminals überleben jedes Ziehen: pane.mounted unverändert
S5

Zoom und Betriebsarten

klein

Der Zoom ist keine Layoutänderung, sondern eine reine Sichtbarkeitsfrage. Das ist die entscheidende Festlegung: Die verdeckten Terminals behalten ihre Größe und werden nicht neu gezeichnet — sonst kostet jedes Ein- und Auszoomen zweimal die volle Neuzeichnung aller Flächen.

VerhaltenWoher
Klick in der Seitenleiste bei aktivem Zoom wechselt den Inhalt, der Zoom bleibtE4
Klick auf einen Chat außerhalb des Workspace verlässt ihnE1
Rückweg über die SeitenleisteE2
Zoom überlebt das Verlassen nichtE6
Zwei Betriebsarten der Hauptansicht: Workspace · EinzelchatFolge aus E1, gehört in den Fenster-Zustand
Abnahme
  • Ein- und Auszoomen ändert keine Terminal-Größe — nachweisbar daran, dass kein neuer Output entsteht
  • Zoom, dann anderen Chat des Workspace anklicken: Inhalt wechselt, Zoom bleibt
  • Workspace verlassen und zurückkehren: Anordnung ist da, Zoom ist weg
S6

Das alte Modell entfernen

mechanisch

In einem Schritt, nicht schrittweise. Zwei Layoutmodelle nebeneinander wären der teuerste Weg: jede Änderung doppelt, und Fehler verstecken sich im Übergang.

Was weg kannUmfang
AgentGridWorkspace.slots, .capacity, allowedCapacities75 Aufrufstellen
AgentGridSplitContainer in seiner heutigen Formersetzt durch WorkspaceLayoutView
Kapazitäts-Auswahl in der Oberflächeersatzlos — das ist der Kern der Beschwerde
Abnahme
  • grep -rn "\.slots\|\.capacity" WhisperM8 liefert nichts mehr
  • Volle Testsuite grün
  • Ein Durchlauf mit scripts/perf-report.sh zeigt keine neuen Budget-Verletzungen gegenüber vorher

Budgets — aus Messungen, nicht geschätzt

MesspunktBudgetHerkunft
grid.dividerTick16 ms60-Hz-Bild. Erreichbar nur mit der Dehn-Technik — 9 Flächen kosten sonst ~24 ms.
Layout berechnen (neu)2 msReine Rechnung ohne I/O; alles darüber deutet auf einen Fehler im Algorithmus.
pane.mounted0 bei LayoutänderungHarte Regel, kein Schwellwert. Jeder Wiederaufbau ist ein Fehler.
sidebar.workspaceChangeFollowUp50 msBestehender Messpunkt vom 02.08.2026
main_thread_freezekeinerBeim Ziehen und Zoomen darf kein einziger auftreten
Abnahme heißt: Budget gerissen = Schritt nicht fertig

Nicht nachher messen, sondern als Bedingung. Das ist die Lehre aus dem 01./02.08.2026: Drei vermeintlich größte Hebel waren Fehlalarme, weil zuerst geschätzt und dann gemessen wurde. Hier steht das Budget vor der Zeile Code.
