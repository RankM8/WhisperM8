Datenmodell — und der Weg dorthin

Das heutige Modell macht die gewünschte Bedienung unmöglich. Hier steht, was an seine Stelle tritt, welche Regeln es dauerhaft einhalten muss und wie der Bestand ohne Verlust hinüberkommt.

Was heute dasteht

WhisperM8/Models/AgentGridWorkspace.swift:15-40

struct AgentGridWorkspace: Identifiable, Codable, Equatable, Hashable {
    var id: UUID
    var name: String
    var colorHex: String
    /// Feste Slot-Positionen; `nil` = sichtbar leerer Slot.
    var slots: [UUID?]
    /// Sichtbare Slot-Anzahl, immer eine erlaubte Stufe.
    var capacity: Int
    var columnFractions: [Double]
    var rowFractions: [Double]

    static let allowedCapacities = [2, 3, 4, 6, 9]
}
Warum daran nichts zu retten ist

Die Position ist die Identität. Ein Chat liegt auf Index 3, und das ist alles, was das Modell über seine Anordnung weiß. Daraus folgt zwingend:

Verdichten würde Positionen ändern — also darf es nicht automatisch passieren. Automatisch anordnen würde Positionen ändern — also darf es das auch nicht. Übrig bleibt Handarbeit. Die Bedienprobleme sind keine fehlenden Funktionen, sie sind die logische Folge dieser einen Entscheidung.

Dazu kommt eine zweite Kopplung: columnFractions und rowFractions hängen an der Stufe. Ändert sich capacity, passt die selbst eingestellte Aufteilung nicht mehr und wird repariert — die Anpassung des Nutzers ist weg.

Was an seine Stelle tritt

Swift-Entsprechung der Engine aus dem HTML-Zwilling, dort mit echter Maus-Interaktion erprobt.

struct AgentWorkspaceLayout: Identifiable, Codable, Equatable {
    var id: UUID
    var name: String
    var colorHex: String

    /// Die Chats, gruppiert in Zellen. Reihenfolge = Lesereihenfolge,
    /// NICHT Bildschirmposition — die berechnet die Engine.
    var cells: [Cell]

    /// Wie die Fläche aufgeteilt wird.
    var arrangement: Arrangement

    /// Absichtlich gestapelt: Chat → Anker-Chat. Überlebt jede
    /// Neuanordnung; ohne das würde Verdichten Stapel zerreißen.
    var bindings: [UUID: UUID]

    /// Kurzzeitiger Gast — sichtbar, aber kein Mitglied.
    var guest: UUID?

    /// Nur bei abgeleiteten Layouts (Projekt-Workspaces): Chats,
    /// die der Nutzer ausgeblendet hat. Löschen geht dort nicht,
    /// weil die Mitgliedschaft aus dem Projekt folgt.
    var hidden: [UUID]

    /// Woher die Mitgliedschaft kommt.
    var source: Source
}

struct Cell: Identifiable, Codable, Equatable {
    var id: UUID
    /// Mindestens ein Eintrag. Leere Zellen existieren nicht —
    /// das ist der Unterschied zu `slots: [UUID?]`.
    var sessions: [UUID]
    /// Welcher davon sichtbar ist. Muss in `sessions` enthalten sein.
    var active: UUID
}

enum Arrangement: Codable, Equatable {
    /// Ergibt sich aus der Zellenzahl. Der Normalfall.
    case automatic
    /// Der Nutzer hat geteilt oder gezogen — sein Baum gilt.
    case manual(SplitNode)
}

indirect enum SplitNode: Codable, Equatable {
    case leaf(cellID: UUID)
    case split(axis: Axis, children: [SplitNode], fractions: [Double])
}

enum Source: Codable, Equatable {
    /// Der Nutzer bestimmt die Mitglieder.
    case manual
    /// Mitglieder folgen aus dem Projekt; `hidden` blendet aus.
    case project(UUID)
}

Die vier Unterschiede, auf die es ankommt

HeuteNeuWas dadurch möglich wird
slots: [UUID?] mit Löcherncells: [Cell], nie leer Schließen verdichtet automatisch. Es gibt kein Loch, das jemand wegräumen müsste.
capacity als EingabeZellenzahl als Tatsache Kein Raster anlegen, kein Verkleinern. Die Anordnung folgt dem Inhalt.
Ein Chat pro PlatzStapel pro Zelle „Als Tab hinzufügen" beim Hineinziehen — mehrere Chats teilen sich eine Fläche.
Feste Gewichte je Stufemanual(SplitNode) nur wenn gewollt Die eigene Aufteilung überlebt, weil sie nicht an einer Stufe hängt.
Warum bindings kein Beiwerk ist

Ohne diese Zuordnung wäre die automatische Anordnung schädlich: Wer zwei Chats bewusst übereinandergelegt hat, verlöre diese Gruppierung beim nächsten Verdichten. bindings hält fest, dass die Stapelung gewollt war — die Engine ordnet frei an, respektiert dabei aber jede ausdrückliche Entscheidung. Das ist der Unterschied zwischen „hilfreich" und „bevormundend".

Invarianten — was nie passieren darf

Jede davon gehört als Test abgesichert, nicht als Kommentar.

RegelWas sie verhindert
Jede Zelle hat mindestens einen ChatGenau das Loch, das im alten Modell entstand. Wird der letzte entfernt, verschwindet die Zelle.
active ist in sessions enthaltenEine Zelle, die auf einen Chat zeigt, den sie nicht hat — dargestellt als leere Fläche ohne Erklärung.
Ein Chat liegt in höchstens einer ZelleZwei Ansichten desselben PTY. Technisch möglich, für den Nutzer verwirrend, und die Fokus-Verwaltung würde mehrdeutig.
Bei manual: jedes Blatt zeigt auf eine existierende Zelle, jede Zelle kommt genau einmal vorChats, die niemand sieht, obwohl sie Mitglied sind — oder doppelt gezeichnete Flächen.
fractions: positiv, endlich, Summe 1, so viele wie KinderFlächen mit Breite 0 oder NaN. Beim heutigen Modell schon einmal aufgetreten.
guest ist kein MitgliedDass eine flüchtige Vorschau versehentlich dauerhaft wird — der Nutzer würde seinen Workspace langsam zumüllen, ohne es zu merken.
Bei source: .project: cells wird abgeleitet, nie direkt gesetztDass die Ableitung und der gespeicherte Stand auseinanderlaufen und niemand weiß, welcher gilt.
Wo die Invarianten durchgesetzt werden

Nicht im Setter und nicht in der Ansicht, sondern in einer Normalisierungsfunktion, durch die jede Änderung läuft — nach demselben Muster wie migratedWorkspace heute. Sie ist pur, damit sie vollständig testbar bleibt: Ein kaputter Zustand hinein, ein gültiger heraus, und der Test beschreibt genau, was „gültig" heißt.

Migration — v4 nach v5

Der Bestand darf nicht verlorengehen, und ein Rückweg muss existieren.

Warum manual und nicht automatic

Die automatische Anordnung ist besser — aber sie ungefragt über eine gewachsene Einrichtung zu legen, fühlt sich wie Datenverlust an, auch wenn keiner vorliegt. Deshalb: Bestand bleibt wie er ist, und ein sichtbarer Schalter („automatisch anordnen") löst ihn auf Wunsch. Neue Workspaces starten dagegen auf automatic — dort gibt es nichts zu bewahren.

Wie groß der Eingriff ist

slots und capacity werden an 75 Stellen im Code benutzt. Das ist die eigentliche Arbeit — nicht der Entwurf des Modells, sondern der Umbau aller Stellen, die vom alten ausgehen.

Daraus folgt die Reihenfolge

Zwei Modelle nebeneinander zu betreiben wäre der teuerste Weg: jede Änderung doppelt, und Fehler verstecken sich im Übergang. Besser ist ein Schnitt, bei dem das alte Modell in einem Schritt verschwindet.

Möglich wird das, wenn die Engine vorher als pure, vollständig getestete Logik steht. Dann ist der Umbau der 75 Stellen mechanisch — und jeder Fehler zeigt sich sofort als fehlgeschlagener Test, nicht erst im Betrieb.
