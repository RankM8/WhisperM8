Workspace-Umbau — Layout, das sich selbst anordnet

Heute muss der Nutzer sein Raster selbst anlegen, verkleinern und umsortieren — und Chats von außen hineinzubekommen ist umständlich. Dieser Plan ersetzt das feste Positionsraster durch eine Anordnung, die sich aus den enthaltenen Chats ergibt.

Warum überhaupt umbauen

Die Bedienprobleme sind keine Oberflächenfrage — sie stehen im Datenmodell.

Ein Workspace ist heute eine Liste fester Plätze:

FeldBedeutungFolge für die Bedienung
slots: [UUID?]Feste Positionen, nil = sichtbar leerEin geschlossener Chat hinterlässt ein Loch. Niemand räumt es weg.
capacity: IntSichtbare Plätze, Stufen 2·3·4·6·9Wächst automatisch, schrumpft nie von selbst — man muss von Hand zurückstellen.
columnFractions
rowFractions		Spalten- und ZeilengewichteHängen an der Stufe; jede Kapazitätsänderung wirft die eigene Aufteilung durcheinander.
Der eigentliche Konstruktionsfehler

Positionsstabilität und automatische Anordnung schließen sich in diesem Modell aus. Weil jeder Chat an einem Index klebt, kann das Layout nicht auf Änderungen reagieren, ohne die Anordnung des Nutzers zu zerstören — und weil es nicht reagieren darf, muss der Nutzer alles von Hand machen. Jede Verbesserung an der Oberfläche stößt an diese Wand.

Die Kernidee — Anordnung ist ein Ergebnis, keine Eingabe

Erprobt im HTML-Zwilling docs/design/agent-chats-layout-engine.html, inklusive echter Maus-Interaktion.

Statt einer Platzliste hält ein Workspace eine Menge von Zellen, und jede Zelle einen Stapel von Chats. Die geometrische Anordnung wird bei jeder Änderung neu berechnet — es sei denn, der Nutzer hat sie ausdrücklich festgelegt.

BegriffWas er trägt
mode: autoDie Anordnung ergibt sich aus der Anzahl der Zellen. Kein Loch, keine Stufe, keine Handarbeit.
mode: snapshotDer Nutzer hat geteilt oder gezogen — ab dann gilt sein Baum, bis er ihn löst.
Zelle mit StapelMehrere Chats teilen sich eine Fläche, einer ist sichtbar. Das ist die Antwort auf „als Tab hinzufügen".
boundMerkt sich, dass ein Chat bewusst zu einem anderen gestapelt wurde — damit die Neuanordnung diese Absicht nicht zerreißt.
guestEin angeklickter Chat erscheint sofort, ohne Mitglied zu werden. Erst ⌥↵ oder ein Zug macht ihn dauerhaft.
Was das für die drei Beschwerden bedeutet

Kein Raster mehr anlegen: Die Anordnung folgt der Anzahl. Kein Verkleinern: Wer einen Chat schließt, verdichtet die Fläche automatisch. Kein Umsortieren: Ziehen tauscht Zellen, statt Indizes zu verschieben. Und „schnell reinhauen" ist ein Klick — der Gast erscheint, ohne dass man vorher Platz schaffen muss.

Risiken — nach Schadenshöhe

RisikoWarum es real istAbsicherung
Terminal wird beim Umsortieren neu aufgebaut Ein PTY neu zu starten heißt: Scrollback weg, laufender Befehl weg. Das wäre schlimmer als jedes Layoutproblem. Der Zähler pane.mounted aus dem Messgerüst deckt jeden ungewollten Wiederaufbau auf. Er gehört in die Abnahme jedes Schritts.
Verlorene Anordnung nach dem Update Wer sich sein Raster mühsam gebaut hat, verliert Vertrauen, wenn es beim Update verschwindet. Migration übernimmt die bestehende Anordnung als snapshot — sie bleibt exakt erhalten, bis der Nutzer selbst auf auto löst.
Drag friert die App ein Genau das ist im Mai 2026 schon passiert (LazyVStack + .draggable, Fix 60ca683). Der Präzedenzfall steht im eigenen Code. Zeigegerät-Ereignisse statt SwiftUIs Drag-API, wie im Zwilling erprobt. Die Auswahl- und Einfüge-Logik bleibt pur und testbar.
Zwei Layout-Modelle nebeneinander Solange beide existieren, verdoppelt sich jede Änderung und Fehler verstecken sich im Übergang. Schnitte so legen, dass das alte Modell in einem Schritt verschwindet, nicht schrittweise.
